# Правила работы с репозиторием

Эти правила рассчитаны на короткий хакатонный цикл и команду из четырёх человек. Цель — держать `main` в рабочем состоянии и быстро объединять frontend с backend.

## Ветки

- `main` — единственная постоянная ветка. В неё попадает только проверенный результат.
- Каждая задача выполняется в короткой ветке от актуальной `main`. Отдельных постоянных веток участников и `develop` нет.
- Формат: `<тип>/<область>-<краткая-задача>` — строчные латинские буквы, цифры и дефисы.

Примеры:

```text
feat/backend-max-auth
feat/frontend-teacher-session
feat/frontend-student-checkin
feat/backend-qr-token
fix/backend-duplicate-checkin
docs/readme-local-run
chore/docker-compose
```

Типы: `feat` — функция, `fix` — исправление, `docs` — документация, `test` — тесты, `chore` — настройка проекта. Области: `frontend`, `backend`, `max`, `docker`, `docs`.

## Рабочий цикл

1. Взять задачу с назначенным владельцем и понятным критерием готовности.
2. Обновить локальную `main`, создать от неё ветку задачи.
3. Делать небольшие коммиты; не добавлять токены, `.env`, реальные данные студентов и тяжёлые временные файлы.
4. Открыть pull request в `main`, заполнить шаблон и указать, как проверена работа.
5. Получить минимум один просмотр другого участника. Изменения на стыке frontend/backend смотрят Никита и Амир; продуктовые тексты и сценарии — Данил или Рома.
6. После исправлений объединить через **Squash and merge** и удалить рабочую ветку.

Если задача блокирует общую демонстрацию, автор сразу сообщает об этом команде. Прямой push в `main` и force push в общие ветки не используем. Для срочного исправления создаём `fix/...` от `main` и проводим тот же короткий review.

## Коммиты и pull request

Заголовок коммита и PR: `<тип>(<область>): <что сделано>`.

Примеры:

```text
feat(backend): validate MAX initData
feat(frontend): show active QR session
fix(backend): reject duplicate check-in
docs(readme): add local launch steps
```

Один PR решает одну задачу. Вместе с изменением API обновляем контракт и сообщаем второй стороне об изменении. В описании PR указываем сценарий проверки, результаты и известные ограничения. Рабочая проверка интеграции Никиты и Амира проходит ежедневно до вечерней демонстрации.

## Перед объединением

- [ ] Изменения соответствуют задаче и не ломают основной сценарий.
- [ ] Код собирается; затронутые тесты и ручной сценарий пройдены.
- [ ] Если изменён API, frontend и backend согласованы.
- [ ] Документация и `.env.example` обновлены при изменении запуска или конфигурации.
- [ ] Секреты и персональные данные отсутствуют в коммитах, логах и примерах.

После feature freeze 27 сентября в 20:00 в `main` принимаем только исправления, необходимые для сдачи или демонстрации. Данил фиксирует финальный commit и tag перед отправкой.
