# Подготовка frontend к запуску

Локальные результаты от 29 сентября 2026 года, ветка `feat/frontend-release-readiness`. Использовались синтетические пользователи и отдельный Compose-проект. Эти результаты не подтверждают развёртывание на публичном сервере или работу в настоящих MAX Mobile/Web.

## Проверено локально

- ESLint, Prettier, TypeScript и production build.
- 16 unit/контрактных тестов, включая отображение аудита и автоматическую отметку студента.
- Production bundle не содержит demo-аккаунтов, пароля, mock-хранилища и `/auth/mock`, даже при `VITE_USE_MOCK_API=true`.
- Docker demo-сборка работает с настоящим backend; production-сборка по умолчанию выполняет проверку bundle.
- Пять E2E-сценариев с реальным backend: основная отметка/закрытие, повторный и атомарно отклонённый CSV-импорт, ручные add/set_status/remove в закрытой сессии с обновлением CSV и аудита, восстановление из истории, сетевой повтор без дубликата, чужая группа и реальный десятисекундный срок QR.
- Два E2E-сценария публичной сборки: вход вне MAX не показывает demo-форму; после сетевой ошибки повтор авторизации читает свежий `initData` и сохраняет путь отметки. В этих двух тестах Bridge и ответы API синтетические; подпись MAX ими не проверяется.
- GitHub workflow `Frontend checks` повторяет локальные проверки и E2E на отдельном Compose-стеке. Его результат на GitHub нужно смотреть для конкретного PR.

Команды запуска приведены в [frontend README](../frontend/README.md). Если стандартные порты приёмочного стека заняты, переопределите `BACKEND_HOST_PORT` и `FRONTEND_HOST_PORT`, а также соответствующие `E2E_API_URL` и `E2E_BASE_URL`. После проверки остановите только свой Compose-проект, сохранив том БД.

## Что ещё подтвердить перед публичным запуском

- Настроить HTTPS-адрес, Mini App URL бота и production backend согласно [checklist развёртывания](production-deploy-checklist.md).
- Подготовить согласованные тестовые MAX-аккаунты через [процедуру подготовки группы](max-test-roster.md).
- На реальном MAX Mobile и MAX Web проверить подписанный вход обеих ролей, `startapp`, автоматическую отметку, восстановление активной сессии, ошибки QR/сети, ручные исправления, историю, CSV и импорт.
- Отдельно подтвердить, что скачивание CSV работает в обоих клиентах и что обычное открытие QR укладывается в его срок. Менять TTL только на одной стороне нельзя.
- Пройти UX на демонстрационных устройствах и подготовить скриншоты/резервное видео на синтетических данных.

Согласованные экраны и операции P0/P1 реализованы. Создание группы через UI, фильтры и пагинация истории — возможные следующие расширения, не обязательные для текущего MVP. Сейчас история ограничена последними 50 занятиями, аудит — последними 500 событиями серверного ответа.
