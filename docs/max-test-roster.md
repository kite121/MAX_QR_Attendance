# Подготовка тестовой группы с реальными аккаунтами MAX

Эта процедура относится только к согласованным тестовым аккаунтам. MAX ID человека может считаться персональными данными: не коммитьте список участников, `initData`, JWT и токен бота. ID, полученный через `GET /me` API MAX, принадлежит **боту**, а не преподавателю.

## До демонстрации

1. У владельцев тестовых аккаунтов получите их MAX user ID через подписанный вход в Mini App: ответ `POST /api/v1/auth/max` содержит `user.max_user_id`. Не используйте `initDataUnsafe.user.id` как доказательство личности — backend доверяет только проверенному `initData`.
2. Укажите MAX ID преподавателя в приватной переменной `BOOTSTRAP_TEACHER_MAX_USER_ID`, а также `BOOTSTRAP_TEACHER_NAME` и `BOOTSTRAP_GROUP_NAME`. Запуск backend создаёт или обновляет преподавателя и связывает его с тестовой группой. После этого преподаватель снова входит через MAX и получает роль `teacher`.
3. Преподаватель получает свой JWT из подписанного входа и ID группы через `GET /api/v1/groups`. Состав группы загружается существующим `POST /api/v1/groups/{group_id}/enrollments/import` как UTF-8 CSV с колонками `max_user_id,display_name`. Имена в тестовом CSV должны быть синтетическими. Файл обрабатывается атомарно; повторный импорт не создаёт дублей. Это подготовка данных перед демонстрацией, не часть пути студента и не ручное редактирование БД.
4. Проверьте `GET /api/v1/groups/{group_id}/students`: там должны быть только подготовленные тестовые аккаунты. Один из них открывает QR в MAX и получает отметку; незачисленный тестовый аккаунт должен увидеть `not_enrolled` и получить отказ `STUDENT_NOT_ENROLLED` при попытке отметки.

Проверка группы означает только наличие MAX ID в составе **этой тестовой группы**. Она не подтверждает реальное зачисление в вуз или физическое присутствие. Права администратора и интеграция с университетским реестром в этот MVP не входят.
